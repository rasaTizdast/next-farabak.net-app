# Farabak Product Storytelling Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: use `.agents/skills/subagent-driven-development/SKILL.md` to implement this plan task by task, with fresh agents and independent reviews. Steps use checkbox (`- [ ]`) syntax for tracking. **This document is a handoff only; the current request does not authorize implementation.**

**Goal:** Replace the generic camera-led landing with a premium, useful five-category product narrative and a published-blog section, while preserving honest proof and fast, accessible baseline content.

**Architecture:** Server-render the hero, category narratives, proof, projects, blog cards, and CTA. Use an asset/content manifest and narrow cached data queries. Place optional focus, scroll, ambient, and any future licensed 3D enhancements in isolated client leaves with static media fallbacks.

**Tech Stack:** Existing Next.js 16.4.2, React 19.3.1, Prisma, TypeScript, CSS Modules, IRANYekan, Motion, Lenis and Three.js. GSAP/ScrollTrigger is conditional after the motion prototype and measurement gate; no dependency addition is part of this planning task.

**Spec:** `docs/superpowers/specs/2026-10-20-farabak-product-storytelling-design.md`

## Global constraints

- Persian/RTL, visible semantic H1, authentic links, keyboard/touch access, reduced-motion and save-data fallback, static first frame.
- Confirmed history is Solar Hijri ۱۳۸۱. No invented partner status, client quote, metrics, certification, installation, price, or inventory promise.
- Every named product must correspond to a current Farabak listing at release. CEIA and SMD route to `/contact-us` until a genuine listing or solution page is verified.
- No exact branded equipment generated by AI; real product imagery requires provenance and reuse approval. No hidden viewer asset extraction.
- Server content remains usable if JavaScript, database feeds, 3D, or motion fail.
- No production data mutation, migrations, deployment, unrelated restyling, or automatic publication.
- Before Next.js code changes, read relevant bundled `node_modules/next/dist/docs/01-app/01-getting-started/{05-server-and-client-components,08-caching,09-revalidating,12-images}.md` and applicable lazy-loading/image guides. Follow the actual 16.4.2 docs, not remembered APIs.
- Preserve unrelated working-tree edits and the shared header/search/account/support/footer.

## Dependencies and decision gates

The plan intentionally has three gates. The baseline design does not wait for any of them:

1. **Assets:** collect approved photos for exact SKUs. If absent, use category-context art with a clear conceptual label, keep an honest contact/category action, and omit exact product claims.
2. **CEIA/SMD commercial offering:** confirm an offered gate and LED wall solution with the business. Until confirmed, do not say OPENGATE or another CEIA model is for sale through Farabak; use `/contact-us`.
3. **3D and GSAP:** only introduce an exact licensed model or GSAP dependency if the conditions in Tasks 5–6 are met. Photography and existing Motion form the complete baseline.

## Interfaces and content schema

Use a data boundary similar to this; an agent should map exact schema fields before implementation:

```ts
type StoryKey = "xray" | "ceia" | "blackmagic" | "cctv" | "smd-wall";
type AssetStatus = "approved-product" | "approved-context" | "conceptual";
type Story = {
  key: StoryKey;
  eyebrow: string;
  title: string;
  intro: string;
  selectionFactors: readonly [string, string, string];
  modelName?: string; // only after live listing recheck
  categoryHref: string;
  actionHref: string; // exact listing or /contact-us
  actionLabel: string;
  mediaKey: string; // validated against asset manifest
  layout: "threshold" | "portal" | "studio" | "field" | "pixels";
};
type BlogCard = {
  id: number;
  title: string;
  href: string;
  topic: string;
  image: string | null;
  imageAlt: string;
  publishedDate: string | null;
  summary: string;
};
```

The manifest stores source, license/approval, real-versus-conceptual status, aspect ratio, mobile crop and fallback. Code must never infer approved usage from a source URL alone.

## Task 2: Data and content boundary

**Deliverable:** Typed story content and a resilient three-card blog query.

- [ ] Add `landing-stories.ts` with the five chapter keys, distinct layout variants, short Persian draft copy from the spec, valid category/contact links, and only reverified named model links. Keep product claims separate from animation labels.
- [ ] Add an independent homepage blog query in `src/lib/data/homepage.ts` selecting only id/title/slug/category/image/alt/date/short description needed for cards. Filter `status: "Published"` and `QrCode_key: null`; require a valid category slug before making a detail URL. Take at most three after topic prioritization (X-ray, Blackmagic, CCTV/Reolink), filling remaining slots by recency. Never load full article HTML, Comments, or Likes for these cards.
- [ ] Use the current cache tag `TAGS.blogs` with a Next 16 supported cache lifetime; verify current blog writes invalidate that tag. Fetch project, showcase, and blog feeds independently (`Promise.allSettled`) so one failure cannot erase others. Distinguish no records from a failed query.
- [ ] Add focused tests for unpublished/QR exclusion, missing category, invalid image/date, deterministic topic choice, and failed-feed fallback. Test behavior rather than duplicating a mapping implementation.

Suggested query shape, to be adapted to actual Prisma relations and Next cache docs:

```ts
const where = { status: "Published", QrCode_key: null };
const select = {
  id: true,
  title: true,
  slug: true,
  image_URL: true,
  image_alt: true,
  created_at: true,
  SEO_description: true,
  BlogCategories: { select: { Categories: { select: { name: true, slug: true } } } },
} as const;
```

Review gate: static story content and homepage data render with blog DB unavailable; no false article, date, count, or link appears.

## Task 4: Public design-system implementation

**Deliverable:** The `DESIGN.md` target applied consistently to the landing page.

- [ ] Map primitive → semantic → component tokens inside `landing.module.css`. Avoid global app token changes. Use navy/paper/silver/blue/cyan in the planned proportions and verify actual text, UI and focus contrast.
- [ ] Use existing IRANYekan weights, two-line H1 at representative widths, 55–75-character reading measure where possible, `<bdi>` or `dir="ltr"` for names, logical margins/padding, and stable image crops.
- [ ] Style navigation, product actions, blog cards, support and closing section with one coherent interaction language. Distinct focus and hover states; at least 44px touch targets. Keep sticky/support overlays from covering chapter controls.
- [ ] Render desktop/mobile full-page screenshots. Compare against the approved composition, not only an absence of errors. Revise a batch of actual visual defects, then inspect again. Request a scoped markup change through the coordinator when CSS alone cannot solve a problem.

## Task 5: Focused Motion and ambient layers

**Deliverable:** An expressive but optional first-class interaction system.

- [ ] Add `ProductRangeFocus.tsx` as a small client leaf. Let the visitor focus a category via click/keyboard; transition the art and short caption with existing Motion. Keep its real anchor navigable. No timed auto-rotation; preserve focus after selection.
- [ ] Add one-time chapter reveals in `LandingExperience.tsx` with initial content visible in server HTML. Use opacity/transform only, subtle stagger, and no motion dependency for page meaning.
- [ ] Add localized low-contrast SVG/CSS background linework to at most 2–3 sections. Before adopting any 21st.dev or React Bits component, inspect its source, license, dependencies, pointer capture, mobile behavior, and reduced-motion state. Prefer a tiny project-specific CSS/SVG derivation over a continuous WebGL shader.
- [ ] Run reduced-motion, save-data, hidden-tab, keyboard, touch, rapid-selection and interrupted-transition checks. Provide pause control for any persistent movement.

## Task 6: Conditional scroll sequence and 3D feasibility

**Deliverable:** Either a justified, measured enhancement or a documented decision to retain the complete baseline.

- [ ] Prototype the short X-ray→CEIA frame transition using existing Motion/CSS first. If it cannot communicate the desired progress-linked transition, use the user's requested GSAP option: inspect ScrollTrigger/useGSAP docs and license, then add only the required packages during implementation.
- [ ] If GSAP is selected, scope one ScrollTrigger timeline to the homepage, use `gsap.matchMedia()` for desktop/reduced-motion, revert on unmount, refresh after media loads, and test anchors with existing Lenis. Choose native scrolling if integration adds friction or jank. Do not add long pinning or multiple scroll owners.
- [ ] Re-evaluate the 3D asset gate from Task 1. If exact, licensed model exists, prototype only one deferred scene with a poster, size budget and disposal. Otherwise keep the photography-driven hero and record that as the final direction. Never scrape model files or fabricate a logo/SKU.
- [ ] Measure frame pacing/interaction on a representative mid-range device and disable or simplify any effect that delays input, obscures copy, or causes layout shift. Reduced-motion path remains static.

## Task 7: SEO, accessibility, and validation

**Deliverable:** Verified public experience and transparent handoff.

- [ ] Update homepage metadata only for copy actually rendered. Maintain canonical and truthful structured data. No unverified affiliation, exact Gregorian founding date, or claim of stocked CEIA/SMD models.
- [ ] Validate H1/H2 order, article headings, link destinations, image alts, decorative `aria-hidden`, button names, keyboard focus, skip link, and contrast. Check no interaction requires drag or hover.
- [ ] Run focused Vitest, ESLint, `tsc --noEmit`, and build where the environment permits. Use `pnpm test -- --pool=threads --maxWorkers=1` for a focused Vitest run if the normal process stalls; a stalled run is unverified. Database `P1001` is a hard stop for claims about persisted/live data, not for document completion.
- [ ] Inspect rendered 320, 360, 390, 768, 1024, and 1440px; test slow/offline-like media failure, blog-empty/error, JS-off static content, reduced motion, save-data, and optional 3D failure. Capture full-page and hero screenshots after assets/fonts settle.
- [ ] Record Lighthouse/field metrics only if actually measured. Aspirational LCP ≤2.5s, INP ≤200ms, CLS ≤0.1 are targets, not acceptance claims from source inspection. Do an independent visual review for editorial rhythm and product credibility before release.
